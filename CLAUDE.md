# riotee-probe-rs

A Rust rewrite of the Python `riotee-probe` CLI tool, structured as a **library plus a thin
binary**. It talks to Riotee Probes and Riotee Boards over CMSIS-DAP (via `probe-rs`) and
drives the two on-module targets: an nRF52 (standard SWD/ARM debug) and an MSP430
(Spy-Bi-Wire, bit-banged by the probe firmware and reached only through vendor commands).

The explicit goal of the rewrite is **code quality**, not feature parity speed.
Prefer good design over a faithful port.
Humans review this code, so readability wins over cleverness.

## Reference material (read-only)

The original implementation is at <https://github.com/NessieCircuits/Riotee_ProbeSoftware>.
In this repo are:
- `firmware/src/probe_vendor.c` — authoritative definition of the vendor command protocol
  (command bytes, payload layout, status bytes).
- `firmware/boards/riotee_{board,probe}.h` — device-specific pin/feature differences.
- `tool/riotee_probe/` — the Python tool being replaced.

`probe-rs` is a pinned git dependency whose vendor-command API is in no published release,
so its docs.rs pages do not describe it. Read the checkout under
`~/.cargo/git/checkouts/probe-rs-*/<rev>/` instead; that is the authoritative source for
what `send_vendor_command`, `DebugProbeSelector` and the flashing progress events actually
do. Registry dependencies are likewise readable under `~/.cargo/registry/src/`.

## Environment

**Sandbox limitation:** any command that enumerates probes (`list`, or anything that opens a
device) panics in a sandbox that lacks `/sys` — the `serialport` crate reads
`/sys/class/tty`. This is not a bug in this crate and cannot be worked around from
application code. Probe-touching code paths can only be tested on real hardware.

## Layout

```
src/lib.rs             # device discovery + the `Riotee<K>` handle; declares the modules below
src/bin/main.rs        # the whole binary: Cli::parse().run()
src/cli.rs             # clap types + `impl Cli { fn run }`; the only place that prints
src/cli/progress.rs    # indicatif FlashProgress rendering — a CLI-only concern
src/error.rs           # `Error`, `ResponseError`, `HexError` and the `Result` alias
src/vendor_commands.rs # the Riotee CMSIS-DAP vendor command protocol (unit-tested)
src/target.rs          # the `Target` trait (reset/halt/resume/program) + `ProgramOptions`
src/target/nrf52.rs    # impl via probe-rs Session
src/target/msp430.rs   # impl via SBW vendor commands
src/intelhex.rs        # hex parsing into word segments (unit-tested)
```

No `mod.rs` files — use `foo.rs` + `foo/` instead.

## Design decisions already made

These were deliberate and argued through; don't quietly undo them.

**Library first, CLI second.** Anything a library user would want must live outside `cli`.
In particular, core logic avoids printing and never renders progress bars: it takes a
`FlashProgress<'_>`, and callers that don't care pass `FlashProgress::empty()`. `list()`
returns data; `cli.rs` formats it.

Printing from the library is undesirable rather than forbidden: where an error genuinely
cannot be returned it may be reported on stderr. `Msp430Session`'s `Drop` is the one such
case today — it warns if the disconnect fails, and offers `disconnect()` so callers that
want the `Result` can opt in.

**Typestate for Board vs Probe.** `Riotee<K>` carries a zero-sized marker (`Board`, `Probe`,
`Unknown`). Board-only methods (`set_bypass`) live in `impl Riotee<Board>`, Probe-only
methods (GPIO) in `impl Riotee<Probe>`, shared ones in the generic impl. The runtime
kind check exists in exactly one place — `Riotee<Unknown>::downcast` — exposed through the
named `try_as_board()` / `try_as_probe()`. Callers use the named methods, not `downcast` with
a turbofish.

**Typesafe vendor commands.** Every vendor command is a struct implementing the `Command`
trait (`const ID: VendorCommandId`, `type Response`, `encode_payload()`,
`parse_response()`), dispatched through `CmsisDapExt::send_riotee_command`. No raw
byte-slicing at call sites. Near-identical commands are generated by the `unit_command!` /
`toggle_command!` macros. This mirrors the SCPI command design in
<https://github.com/MatzeS/spd3303x>; follow that style when adding commands.

**Responses are parsed by consuming a cursor.** `parse_response` takes `&mut &[u8]` and
advances it through `read_u8` / `read_u16` / `read_all`; `send_riotee_command` then calls
`check_empty`, so leftover bytes are a protocol error. Emptiness is the caller's check, not
each parser's — also from the SCPI crate above.

**Commands validate at construction.** Where the firmware cannot express a request,
the command struct keeps its fields private and `new()` returns a `Result`
(`GpioSet`/`GpioGet` on the pin, `SbwRead`/`SbwWrite` on the word count). This is load
bearing: the firmware indexes its GPIO table and sizes its SBW buffers without checking
either, so an unchecked request corrupts memory on the probe and still answers `DAP_OK`.

**Extension traits over probe-rs types** rather than wrapper types:
`CmsisDapExt::send_riotee_command`, `DebugProbeSelectorExt::is_riotee` / `riotee_kind`.

**A typed error, except in the CLI.** The library returns `error::Error`, with
`ResponseError` and `HexError` nested under it for the two groups that share a context.
`cli.rs` and `bin/main.rs` keep `anyhow` on purpose: its `Debug` prints the whole `source`
chain, which a bare error type does not. `Cli::run` bridges with one `Ok(result?)`.

**Firmware formats are not detected.** The nRF52 takes an ELF and the MSP430 takes Intel
HEX, chosen by the target, never by sniffing the file or its extension. probe-rs behaves
the same way and simply defaults to ELF.

**`open` refuses to guess.** Unlike probe-rs, which opens the first device a selector
matches, `Riotee::open` fails when several match and lists them. This tool writes firmware;
silently choosing between two identical boards can flash the wrong one.

**Comments carry what the code cannot.** Facts from outside the file earn a comment — what
the firmware does, why a dependency behaves unexpectedly, why an alternative was rejected.
Restating the next line does not, and neither do doc comments on self-evident constants.
Prefer putting the explanation in the error message over commenting the check.

**Dependencies use exact resolved semver triples** (`anyhow = "1.0.104"`, not `"1"`), and
`probe-rs` is pinned to an upstream git rev. Use **upstream probe-rs**, never a fork — it
supports dynamic vendor commands.
